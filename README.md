# GLYPH ASCII Studio

安装：`npm ci`

本地启动：`npm run dev`

类型检查：`npm run typecheck`

单元测试（三方合并引擎 + 工程包校验）：`npm test`

生产构建：`npm run build`

Docker 启动：`docker compose up --build`，访问 http://localhost:18018。

## 离线作品交接与三方合并

所有交接数据都在浏览器本地处理，不上传任何服务器。

### 工程包格式（`.glyphtx.json`，版本化）

- `kind / version`：格式标识与版本号；高于本机支持版本的工程会被拦截，不会进入作品库。
- `projectId` + 完整 `revisions` 修订链：记录**共同来源**，接收方据此定位最近共同祖先（merge base）。
- 两种资源模式：
  - `embedded` 完整内嵌：原图以 data URL 单文件打包，可离线交接；
  - `dedup` 内容去重引用：只携带 SHA-256 哈希，接收方必须在本机作品库持有相同内容，否则判定为断裂引用。

### 交接流程

1. 在 `04 / HANDOFF` 面板把当前作品「保存到作品库」：原图按内容哈希存入 IndexedDB，状态形成修订链。
2. 「导出交接工程」生成 `.glyphtx.json` 发给接收方。
3. 接收方「导入」时工程先进入**临时区**，逐项校验通过前不会触碰本机作品库。

### 临时区校验（全部通过才允许合并）

- 非法 JSON / 格式标识错误 / 结构缺失；
- 未来版本、旧版本兼容提示；
- 内嵌资源哈希不匹配、图片无法解码、超尺寸等**损坏文件**；
- 资源清单缺失、去重引用在本机无法解析等**断裂引用**。

### 三方合并（绝不按导入时间覆盖）

以共同来源为 base、本机为 local、对端为 remote 做**字段级**三路对比：

| 情形 | 行为 |
| --- | --- |
| 一方只改裁剪、另一方只改字符规则 | 非重叠修改自动组合 |
| 双方修改同一参数且取值不同 | 标记为**冲突**，必须逐项显式选择 |
| 双方都更换原图（哈希不同） | 标记为**冲突**，显式二选一 |
| 双方做了相同修改 | 识别为一致修改，不产生冲突 |
| 没有共同祖先 | 拒绝合并 |

合并预览弹窗支持逐项选择，并按当前选择用同一套生成逻辑**重新生成同布局的字符图片与文本**；「取消」只关闭会话，临时区与双方工程完整保留。

### 原子性、容量与可追溯

- 合并提交是单个 IndexedDB 事务：资源、对端修订、合并修订、合并留痕、head 更新与临时区清理要么全部成功，要么整体回滚。
- 提交前做容量预检，预留 15% 余量；**存储空间不足不会留下半次合并**。
- 每次合并的共同来源修订、对端头、逐项选择与最终状态写入 `merges` 表，重新打开应用后可在「合并追溯」中查看结果由哪些选择产生。
